# Amazake

Серверное ядро Minecraft **1.21.11**: форк [Paper](https://github.com/PaperMC/Paper). Цель — многопоточное, быстрое и удобное ядро для любых серверов: работают обычные плагины Paper, а каждая многопоточная фича включается переключателем в `amazake.yml`.

## Устройство

Как у всех форков Paper (Purpur, Leaf…): в репозитории **только наши патчи**. Paper и код Minecraft не хранятся. [paperweight](https://github.com/PaperMC/paperweight) скачивает Paper на закреплённом коммите, Minecraft — у Mojang, накладывает наши патчи и собирает paperclip-jar. При запуске jar сам скачивает ванильный сервер.

| Путь | Что |
|---|---|
| `gradle.properties` | Версия Minecraft и коммит Paper (`paperCommit`) |
| `amazake-server/minecraft-patches/` | Патчи к коду Minecraft: `sources/` — по файлу, `features/` — крупные изменения коммитами |
| `amazake-server/paper-patches/` | Патчи к серверной части Paper (CraftBukkit и сам Paper) |
| `amazake-server/src/` | Наши собственные классы сервера |
| `amazake-api/paper-patches/` | Патчи к API (то, что видят плагины) |
| `amazake-*/build.gradle.kts.patch` | Сборка: подключение форка, ребрендинг |
| `build-data/amazake.at` | Access transformers: открыть приватные поля и методы Minecraft |

## Скачать

Последняя сборка: **https://github.com/tearsmilk/amazake/releases/latest** (`amazake-1.21.11-N.jar`).

Запускается как обычный Paper: положите jar в папку сервера и запустите `java -jar amazake-1.21.11-N.jar --nogui`. Ванильный сервер jar докачивает сам.

## Сборка

Нужны JDK 21 и git.

```bash
./gradlew applyAllPatches
```

```bash
./gradlew createMojmapPaperclipJar
```

Готовый сервер появится в `amazake-server/build/libs/amazake-paperclip-1.21.11-R0.1-SNAPSHOT-mojmap.jar`.

Каждый пуш в `main` GitHub Actions собирает сам. Перед публикацией собранный сервер запускается, и проверяются `/version`, `/amazake`, `/spark` и `amazake.yml`. Если всё прошло, jar выкладывается в Releases.

## Команды и права

| Команда | Право | Что делает |
|---|---|---|
| `/amazake version` | `amazake.command` | Версия сборки |
| `/amazake reload` | `amazake.command.reload` | Перечитать `amazake.yml` |
| `/amazake profile [секунды]` | `amazake.command.profile` | Замерить нагрузку сервера и получить отчёт (см. «Профайлер») |
| `/amazake profile stop` | `amazake.command.profile` | Закончить замер раньше и сразу получить отчёт |
| `/amazake cores` | `amazake.command.cores` | Раскладка ядер: какое ядро чем занято, загрузка каждого ядра за последнюю секунду и где работают потоки (см. «Раскладка ядер») |
| `/spark …` | `spark` | Встроенный профайлер spark из Paper (`/spark profiler`, `/spark tps`, `/spark health`) |

По умолчанию эти права есть только у OP. Из консоли команды работают всегда.

Для подкоманд `/amazake …` нужно ещё и общее право `amazake.command`.

## Профайлер

`/amazake profile [секунды]` замеряет сервер (по умолчанию 30 с, не дольше `profiler.max-seconds`): загрузку каждого ядра, CPU сервера по потокам и группам потоков (главный поток, генерация и загрузка чанков, сеть, GC, JIT, плагины…), TPS и MSPT, лаги дольше 50 мс, память, сборки мусора, игроков, сущности и чанки. Одновременно идёт только один замер; замер работает в своём потоке и не нагружает главный.

Куда попадает отчёт:

- **На ваш сайт профайлера** — если в `amazake.yml` указан `profiler.upload-url` (например `https://profiler.example.com`). Сервер отправляет отчёт на `<адрес>/api/reports` и присылает кликабельную ссылку вида `https://profiler.example.com/r/<id>`. Если сайт просит токен, впишите его в `profiler.upload-token`.
- **В файл** — если `profiler.upload-url` пустой или отправить не удалось: `profiles/amazake-profile-<дата-время>.json` в папке сервера. Этот файл можно просто перетащить на страницу сайта профайлера, и он откроется так же, как по ссылке. Если сервер выключают во время замера, отчёт сразу сохраняется в файл, без отправки на сайт.

Настройки в `amazake.yml` (применяются через `/amazake reload`):

| Настройка | По умолчанию | Что |
|---|---|---|
| `profiler.upload-url` | `""` | Адрес сайта профайлера; пусто — только файлы |
| `profiler.upload-token` | `""` | Токен для сайта (заголовок `X-Amazake-Token`) |
| `profiler.default-seconds` | `30` | Длина замера без аргумента |
| `profiler.max-seconds` | `600` | Самый долгий замер |
| `profiler.interval-ms` | `1000` | Интервал между выборками, от 250 до 4000 мс |

Формат отчёта и API сайта описаны в [`docs/profiler-format.md`](docs/profiler-format.md).

## Раскладка ядер

Каждое ядро процессора получает свою работу. Потоки сервера делятся на роли, и каждая роль закрепляется за своими ядрами, чтобы тяжёлая генерация чанков или фоновые задачи плагинов не отнимали время у главного потока:

| Роль | Какие потоки |
|---|---|
| `tick` | Главный поток (`Server thread`): тики миров, сущности, редстоун |
| `chunks` | Пул чанков Paper: генерация, загрузка, свет, чтение и запись регионов |
| `network` | Сеть (Netty): пакеты, сжатие, шифрование |
| `gc` | Сборщик мусора, JIT-компилятор и служебные потоки JVM |
| `background` | Всё остальное: асинхронные задачи плагинов, чат, фоновые задачи Paper, spark |

**Раскладка не делает тик быстрее.** Один тик по-прежнему выполняется на одном ядре; раскладка только не пускает на ядро главного потока чужую работу. Остальным задачам при этом достаётся меньше ядер, чем без неё: чанки, сеть и фон делят оставшиеся ядра, а на 2–4 ядрах роли ещё и делят одно ядро на двоих. Если после включения TPS стал хуже или чанки грузятся медленнее, выключите раскладку (`cpu.layout.enabled: false`) или дайте ролям больше ядер вручную. Паузы сборщика мусора (потоки `GC Thread#N` у G1 и Parallel GC) раскладка не ограничивает: в паузе главный поток всё равно стоит, и сборщик работает на всех ядрах. Рабочие потоки ZGC и Shenandoah работают одновременно с тиками, поэтому получают все ядра, кроме ядра `tick`.

Работает только на **Linux**, если серверу доступно хотя бы 2 логических ядра. Нужны:

- команда `taskset` из пакета `util-linux` (есть почти везде; в минимальном Docker-образе поставьте `util-linux`);
- флаг запуска `-XX:ActiveProcessorCount=<число ядер>`, например `java -XX:ActiveProcessorCount=12 -jar amazake.jar --nogui`. Java считает ядра по тем, что разрешены потоку: без флага после раскладки главный поток «видит» одно ядро, и плагины, которые создают пулы потоков по числу ядер в `onEnable`, делают их из одного потока. Поэтому без флага Amazake раскладку только рассчитывает и показывает, но не применяет, и пишет в консоль, какой флаг добавить. Применить её без флага можно настройкой `cpu.layout.ignore-processor-count: true`.

Отдельный поток `Amazake Cores` раз в секунду находит новые потоки и закрепляет их; главный поток он не нагружает (на уже закреплённые потоки уходит одно чтение имени из `/proc`). Новый поток в Linux получает ядра того, кто его создал, поэтому поток, который создал главный поток (задача плагина, новый поток пула), до секунды работает на ядре `tick`, пока его не перенесут. Если `taskset` нет или система запрещает менять привязку (бывает в контейнерах), Amazake один раз пишет об этом в консоль и работает дальше без раскладки. Если ядро выключили на ходу (VM, hotplug), раскладка один раз пересчитывается для оставшихся ядер.

Как ядра делятся сами (`auto`), если серверу доступно N логических ядер. Номера — как в Linux и в `cpu.layout`, с нуля, среди ядер, доступных серверу (если серверу даны ядра 4–7, то «0» в таблице — это ядро 4):

| N | tick | chunks | gc | network | background |
|---|---|---|---|---|---|
| 1 | раскладка выключена | | | | |
| 2 | 0 | 1 | 1 | 1 | 1 |
| 3 | 0 | 1 | 1 | 2 | 2 |
| 4 | 0 | 1 | 2 | 3 | 3 |
| 5 и больше | одно физическое ядро | ≈40% остальных | ≈15% остальных | 1 | остальные |

Начиная с 5 ядер главный поток получает первое физическое ядро. Если у процессора есть SMT (Hyper-Threading), второй поток этого ядра остаётся свободным, когда ядер 8 и больше, чтобы главному потоку ничто не мешало; на меньших машинах он отходит к `background`. Остальные ядра раздаются целыми физическими ядрами: сначала `chunks`, потом `gc`, `network` и `background`. Например, на 12 ядрах без SMT: `tick=[0] chunks=[1-4] network=[7] gc=[5-6] background=[8-11]`. Если на вашей машине ядро 0 занято прерываниями (сетевая карта, диски — видно в `/proc/interrupts`), перенесите главный поток: `cpu.layout.tick: "11"`.

Если контейнер ограничен квотой CPU (Docker `--cpus`, лимит CPU в Pterodactyl), а не набором ядер (`--cpuset-cpus`), сервер видит все ядра хоста, но может занять только часть их времени. Закреплять главный поток за одним ядром хоста тогда вредно, и автоматическая раскладка выключается (строка `Amazake cores: disabled (CPU quota ...)`). Ручные списки в `cpu.layout` в этом случае применяются с предупреждением, а пул чанков не получает потоков больше квоты.

Пул чанков Paper получает столько потоков, сколько ядер у `chunks` (если в `paper-global.yml` не задан свой `chunk-system.worker-threads`). При запуске сервер пишет раскладку в консоль одной строкой (`Amazake cores: tick=[0] chunks=[1] ...` или `Amazake cores: disabled (причина)`) и таблицей. `/amazake cores` показывает её вместе с загрузкой каждого ядра и тем, сколько потоков каждой группы на каких ядрах сейчас работает.

Настройки в `amazake.yml` (применяются через `/amazake reload`):

| Настройка | По умолчанию | Что |
|---|---|---|
| `cpu.layout.enabled` | `true` | Включить раскладку. При выключении потоки снова получают все ядра |
| `cpu.layout.tick` | `auto` | Ядра главного потока |
| `cpu.layout.chunks` | `auto` | Ядра чанков |
| `cpu.layout.network` | `auto` | Ядра сети |
| `cpu.layout.gc` | `auto` | Ядра GC, JIT и служебных потоков JVM |
| `cpu.layout.background` | `auto` | Ядра всего остального |
| `cpu.layout.resize-chunk-pool` | `true` | Подогнать размер пула чанков под число ядер `chunks` |
| `cpu.layout.ignore-processor-count` | `false` | Применять раскладку и без флага `-XX:ActiveProcessorCount` |

Вместо `auto` можно указать ядра вручную, номерами как в Linux (с нуля): `"0"`, `"1-3"`, `"1,2,5"`, `"0-3,8-11"`. Ядра, которые заняла ручная роль, убираются из автоматических ролей; свободные ядра достаются `background`. Ядра, недоступные серверу, и ошибки в списке Amazake пропускает и пишет об этом в консоль. После `/paper reload` размер пула чанков возвращается к настройке Paper: выполните `/amazake reload`, чтобы снова подогнать его (после `/reload` Bukkit это происходит само).

## Как вносить изменения

1. `./gradlew applyAllPatches`. Появятся `paper-server/`, `paper-api/` и `amazake-server/src/minecraft/` — git-репозитории с кодом.
2. Правите код там и делаете коммиты внутри этих папок (один коммит — один патч).
3. Пересобираете патчи. Для API и одиночных файлов Paper — `./gradlew rebuildPaperPatches`. Полный список задач пересборки серверной части выводит `./gradlew tasks --all | grep -i rebuild`.
4. Коммитите изменённые файлы `*-patches/` в этот репозиторий.

Собственные классы Amazake (не патчи) лежат в `amazake-server/src/main/java/ink/hoka/amazake/`.

Отмечайте изменения в коде Minecraft и Paper комментариями `// Amazake - что и зачем`, а блоки — `// Amazake start - …` и `// Amazake end - …`. Так при обновлении Paper сразу видно, где наш код.

Проверить локально: `./gradlew runDevServer`.
