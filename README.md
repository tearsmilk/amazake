# Amazake

Серверное ядро Minecraft **1.21.11**: форк [Paper](https://github.com/PaperMC/Paper). Цель — многопоточное, быстрое и удобное ядро для любых серверов: работают обычные плагины Paper, а каждая многопоточная фича включается переключателем в `amazake.yml`.

## Устройство

Как у всех форков Paper (Purpur, Leaf…): в репозитории **только наши патчи**. Paper и код Minecraft не хранятся. [paperweight](https://github.com/PaperMC/paperweight) скачивает Paper на закреплённом коммите, Minecraft — у Mojang, накладывает наши патчи и собирает paperclip-jar. При запуске jar сам скачивает ванильный сервер.

| Путь | Что |
|---|---|
| `gradle.properties` | Версия Minecraft и коммит Paper (`paperCommit`) |
| `amazake-server/minecraft-patches/` | Патчи к коду Minecraft: `sources/` — по файлу, `features/` — крупные изменения коммитами |
| `amazake-server/paper-patches/` | Патчи к серверной части Paper (CraftBukkit и сам Paper) |
| `amazake-server/src/` | Наши собственные классы сервера |
| `amazake-api/paper-patches/` | Патчи к API (то, что видят плагины) |
| `amazake-*/build.gradle.kts.patch` | Сборка: подключение форка, ребрендинг |
| `build-data/amazake.at` | Access transformers: открыть приватные поля и методы Minecraft |

## Скачать

Последняя сборка: **https://github.com/tearsmilk/amazake/releases/latest** (`amazake-1.21.11-N.jar`).

Запускается как обычный Paper: положите jar в папку сервера и запустите `java -jar amazake-1.21.11-N.jar --nogui`. Ванильный сервер jar докачивает сам.

## Сборка

Нужны JDK 21 и git.

```bash
./gradlew applyAllPatches
```

```bash
./gradlew createMojmapPaperclipJar
```

Готовый сервер появится в `amazake-server/build/libs/amazake-paperclip-1.21.11-R0.1-SNAPSHOT-mojmap.jar`.

Каждый пуш в `main` GitHub Actions собирает сам. Перед публикацией собранный сервер запускается, и проверяются `/version`, `/amazake`, `/spark` и `amazake.yml`. Если всё прошло, jar выкладывается в Releases.

## Команды и права

| Команда | Право | Что делает |
|---|---|---|
| `/amazake version` | `amazake.command` | Версия сборки |
| `/amazake reload` | `amazake.command.reload` | Перечитать `amazake.yml` |
| `/amazake profile [секунды]` | `amazake.command.profile` | Замерить нагрузку сервера и получить отчёт (см. «Профайлер») |
| `/amazake profile stop` | `amazake.command.profile` | Закончить замер раньше и сразу получить отчёт |
| `/amazake cores` | `amazake.command.cores` | Раскладка ядер: какое ядро чем занято, загрузка каждого ядра за последнюю секунду и где работают потоки (см. «Раскладка ядер») |
| `/spark …` | `spark` | Встроенный профайлер spark из Paper (`/spark profiler`, `/spark tps`, `/spark health`) |

По умолчанию эти права есть только у OP. Из консоли команды работают всегда.

Для подкоманд `/amazake …` нужно ещё и общее право `amazake.command`.

## Профайлер

`/amazake profile [секунды]` замеряет сервер (по умолчанию 30 с, не дольше `profiler.max-seconds`): загрузку каждого ядра, CPU сервера по потокам и группам потоков (главный поток, генерация и загрузка чанков, сеть, GC, JIT, плагины…), TPS и MSPT, лаги дольше 50 мс, память, сборки мусора, игроков, сущности и чанки. Одновременно идёт только один замер; замер работает в своём потоке и не нагружает главный.

Куда попадает отчёт:

- **На ваш сайт профайлера** — если в `amazake.yml` указан `profiler.upload-url` (например `https://profiler.example.com`). Сервер отправляет отчёт на `<адрес>/api/reports` и присылает кликабельную ссылку вида `https://profiler.example.com/r/<id>`. Если сайт просит токен, впишите его в `profiler.upload-token`.
- **В файл** — если `profiler.upload-url` пустой или отправить не удалось: `profiles/amazake-profile-<дата-время>.json` в папке сервера. Этот файл можно просто перетащить на страницу сайта профайлера, и он откроется так же, как по ссылке. Если сервер выключают во время замера, отчёт сразу сохраняется в файл, без отправки на сайт.

Настройки в `amazake.yml` (применяются через `/amazake reload`):

| Настройка | По умолчанию | Что |
|---|---|---|
| `profiler.upload-url` | `""` | Адрес сайта профайлера; пусто — только файлы |
| `profiler.upload-token` | `""` | Токен для сайта (заголовок `X-Amazake-Token`) |
| `profiler.default-seconds` | `30` | Длина замера без аргумента |
| `profiler.max-seconds` | `600` | Самый долгий замер |
| `profiler.interval-ms` | `1000` | Интервал между выборками, от 250 до 4000 мс |
| `profiler.entity-breakdown` | `true` | Во время замера считать время тика сущностей (вкладка «Сущности») |
| `profiler.plugin-breakdown` | `true` | Во время замера считать время каждого плагина в главном потоке и процессор его асинхронных задач (вкладка «Плагины») |

**Сущности.** Во время замера сервер считает, куда уходит время тика сущностей: мобы (всё с ИИ), остальные сущности (предметы, опыт, падающие блоки, стрелы, вагонетки, стойки) и игроки. Время каждого типа сущности раскладывается по фазам: цели, мозг, сенсоры, поиск пути, движение по пути, физика движения, коллизии, толкотня, подбор предметов, жидкости, слияние предметов и опыта, неактивные тики. На сайте это вкладка «Сущности». Вне замера счётчики выключены и ничего не стоят. Стресс-плагин AmazakeStress на Amazake пишет эти же цифры для каждого этапа теста.

**Плагины.** Код плагинов, который трогает мир (синхронные задачи планировщика, обработчики синхронных событий, команды), Amazake оставляет в главном потоке, как в Bukkit: так не бывает гонок данных. Во время замера сервер измеряет этот «мост» для каждого плагина отдельно: сколько миллисекунд за тик заняли его задачи, события и команды (собственное время: обработчик другого плагина, вызванный из задачи, засчитывается своему плагину), сколько было вызовов и сколько процессора съели его асинхронные задачи (Bukkit `runTaskAsynchronously` и Folia `AsyncScheduler`). После замера в чат приходит строка вроде «Плагины в главном потоке: 3.4 мс/тик (AmazakeStress 2.9, LuckPerms 0.3)», на сайте это вкладка «Плагины». Вне замера счётчики выключены и ничего не стоят.

Формат отчёта и API сайта описаны в [`docs/profiler-format.md`](docs/profiler-format.md).

## Раскладка ядер

Каждое ядро процессора получает свою работу. Потоки сервера делятся на роли, и каждая роль закрепляется за своими ядрами, чтобы тяжёлая генерация чанков или фоновые задачи плагинов не отнимали время у главного потока:

| Роль | Какие потоки |
|---|---|
| `tick` | Главный поток (`Server thread`): тики миров, сущности, редстоун |
| `chunks` | Пул чанков Paper: генерация, загрузка, свет, чтение и запись регионов |
| `network` | Сеть (Netty): пакеты, сжатие, шифрование |
| `gc` | Сборщик мусора, JIT-компилятор и служебные потоки JVM |
| `plugins` | Асинхронная работа плагинов: асинхронные задачи планировщика (`Craft Scheduler Thread`), асинхронный чат и автодополнение, пулы асинхронных событий входа и настройки (`User Authenticator`, `Configuration Thread`), потоки, которые плагины создали сами |
| `background` | Поддержка (ядро-подложка): фоновые задачи Paper, spark, Amazake. Сюда же с приоритетом переливаются потоки плагинов |

**Плагины и гонки данных.** Код плагинов, который трогает мир — синхронные задачи планировщика, обработчики событий, команды, — как и в Bukkit, выполняется в главном потоке, между тиками и внутри них, по очереди с игрой: Amazake не переносит его в другие потоки, поэтому гонок с тиком нет и плагины работают как обычно. На ядра `plugins` уходит только то, что плагины и так делают асинхронно. Сколько каждый плагин занимает в главном потоке, показывает вкладка «Плагины» отчёта профайлера (`profiler.plugin-breakdown`).

Потоки, которые плагин создал сам (`new Thread`, свои пулы), не узнать по имени. Amazake раз в секунду смотрит на новые потоки: если класс потока или его загрузчик классов — плагина, или в его стеке есть классы из jar-файла плагина, поток попадает в группу `plugins-own` и переезжает на ядра `plugins`. Поток пула, который всё время ждёт работы, может определиться позже: стек перепроверяется не чаще раза в 30 секунд и только если поток с прошлой проверки работал (все стеки за проверку читаются одной короткой паузой JVM). Потоки плагинов работают не только на своих ядрах, но и на ядрах `background` (ядро-подложка), а фоновым потокам там (spark, Amazake, служебные потоки Paper) Amazake понижает приоритет: `nice 5` (`cpu.layout.support-nice`), так что при споре за ядро потоки плагинов получают его примерно втрое чаще. Главный поток, сеть, чанки, GC и потоки плагинов приоритет не меняют никогда, как и потоки `ForkJoinPool` (общий пул, через который плагины часто работают асинхронно: `CompletableFuture.supplyAsync`, параллельные потоки). Без права `CAP_SYS_NICE` приоритет можно только понизить: после выключения раскладки он остаётся до перезапуска сервера.

**Раскладка не делает тик быстрее.** Один тик по-прежнему выполняется на одном ядре; раскладка только не пускает на ядро главного потока чужую работу. Остальным задачам при этом достаётся меньше ядер, чем без неё: чанки, сеть и фон делят оставшиеся ядра, а на 2–4 ядрах роли ещё и делят одно ядро на двоих. Если после включения TPS стал хуже или чанки грузятся медленнее, выключите раскладку (`cpu.layout.enabled: false`) или дайте ролям больше ядер вручную. Паузы сборщика мусора (потоки `GC Thread#N` у G1 и Parallel GC) раскладка не ограничивает: в паузе главный поток всё равно стоит, и сборщик работает на всех ядрах, кроме резервных. Рабочие потоки ZGC и Shenandoah работают одновременно с тиками, поэтому получают все ядра, кроме ядра `tick`.

Работает только на **Linux**, если серверу доступно хотя бы 2 логических ядра. Нужны:

- команда `taskset` из пакета `util-linux` (есть почти везде; в минимальном Docker-образе поставьте `util-linux`);
- флаг запуска `-XX:ActiveProcessorCount=<число ядер>`, например `java -XX:ActiveProcessorCount=12 -jar amazake.jar --nogui`. Java считает ядра по тем, что разрешены потоку: без флага после раскладки главный поток «видит» одно ядро, и плагины, которые создают пулы потоков по числу ядер в `onEnable`, делают их из одного потока. Поэтому без флага Amazake раскладку только рассчитывает и показывает, но не применяет, и пишет в консоль, какой флаг добавить. Применить её без флага можно настройкой `cpu.layout.ignore-processor-count: true`.

Отдельный поток `Amazake Cores` раз в секунду находит новые потоки и закрепляет их; главный поток он не нагружает (на уже закреплённые потоки уходит одно чтение имени из `/proc`). Новый поток в Linux получает ядра того, кто его создал, поэтому поток, который создал главный поток (задача плагина, новый поток пула), до секунды работает на ядре `tick`, пока его не перенесут. Если `taskset` нет или система запрещает менять привязку (бывает в контейнерах), Amazake один раз пишет об этом в консоль и работает дальше без раскладки. Если ядро выключили на ходу (VM, hotplug), раскладка один раз пересчитывается для оставшихся ядер.

Как ядра делятся сами (`auto`), если серверу доступно N логических ядер. Номера — как в Linux и в `cpu.layout`, с нуля, среди ядер, доступных серверу (если серверу даны ядра 4–7, то «0» в таблице — это ядро 4):

| N | tick | chunks | gc | plugins | network | background | резерв |
|---|---|---|---|---|---|---|---|
| 1 | раскладка выключена | | | | | | |
| 2 | 0 | 1 | 1 | 1 | 1 | 1 | — |
| 3 | 0 | 1 | 1 | 2 | 2 | 2 | — |
| 4 | 0 | 1 | 2 | **3** | 2 | 2 | — |
| 5 | 0 | 1 | 2 | **3** | 4 | 4 | — |
| 6 без SMT | 0 | 1 | 2 | **3** | 4 | 4 | 5 |
| 6 с SMT (3 физ. ядра) | 0 | 2 | 3 | **4** | 5 | 1 | — |
| 8 без SMT | 0 | 1–3 | 4 | **5** | 6 | 6 | 7 |
| 8 с SMT | 0 (1 свободно) | 2–3 | 4 | **5** | 4 | 4 | 7 (6 свободно) |
| больше | одно физическое ядро | ≈40% остальных | ≈15% остальных | ≈15% остальных | 1 | остальные | 1 |

Своё ядро у плагинов появляется с 4 ядер; на 2–3 ядрах они делят ядро с сетью и поддержкой. SMT-пары в таблице — соседние номера (0 и 1, 2 и 3...).

Начиная с 5 ядер главный поток получает первое физическое ядро. Если у процессора есть SMT (Hyper-Threading), второй поток этого ядра остаётся свободным, когда ядер 8 и больше, чтобы главному потоку ничто не мешало; на меньших машинах он отходит к `background`. Остальные ядра раздаются целыми физическими ядрами: сначала `chunks`, потом `gc`, `plugins`, `network` и `background`. Начиная с 6 ядер одно ядро из `background` уходит в резерв (см. «Резерв и переезд тика» ниже); если `background` при этом пустеет, поддержка делит ядро с сетью (или с GC), а своё ядро `plugins` остаётся только плагинам. Например, на 6 ядрах без SMT: `tick=[0] chunks=[1] network=[4] gc=[2] plugins=[3] background=[4] reserve=[5]` — потоки плагинов работают на ядре 3 и на ядре-подложке 4; на 12 ядрах без SMT: `tick=[0] chunks=[1-4] network=[9] gc=[5-6] plugins=[7-8] background=[10] reserve=[11]`; на 16 ядрах с SMT: `tick=[0] chunks=[2-7] network=[12] gc=[8-9] plugins=[10-11] background=[13] reserve=[15]`. Если на вашей машине ядро 0 занято прерываниями (сетевая карта, диски — видно в `/proc/interrupts`), перенесите главный поток: `cpu.layout.tick: "11"`.

Если контейнер ограничен квотой CPU (Docker `--cpus`, лимит CPU в Pterodactyl), а не набором ядер (`--cpuset-cpus`), сервер видит все ядра хоста, но может занять только часть их времени. Закреплять главный поток за одним ядром хоста тогда вредно, и автоматическая раскладка выключается (строка `Amazake cores: disabled (CPU quota ...)`). Ручные списки в `cpu.layout` в этом случае применяются с предупреждением, а пул чанков не получает потоков больше квоты.

Пул чанков Paper получает столько потоков, сколько ядер у `chunks` (если в `paper-global.yml` не задан свой `chunk-system.worker-threads`). При запуске сервер пишет раскладку в консоль одной строкой (`Amazake cores: tick=[0] chunks=[1] ...` или `Amazake cores: disabled (причина)`) и таблицей. `/amazake cores` показывает её вместе с загрузкой каждого ядра и тем, сколько потоков каждой группы на каких ядрах сейчас работает, а строкой «Плагины: ...» — своё ядро плагинов, ядро-подложку и сколько своих потоков плагинов найдено.

Настройки в `amazake.yml` (применяются через `/amazake reload`):

| Настройка | По умолчанию | Что |
|---|---|---|
| `cpu.layout.enabled` | `true` | Включить раскладку. При выключении потоки снова получают все ядра |
| `cpu.layout.tick` | `auto` | Ядра главного потока |
| `cpu.layout.chunks` | `auto` | Ядра чанков |
| `cpu.layout.network` | `auto` | Ядра сети |
| `cpu.layout.gc` | `auto` | Ядра GC, JIT и служебных потоков JVM |
| `cpu.layout.plugins` | `auto` | Ядра асинхронной работы плагинов. `auto`: своё ядро (≈15% остальных) от 4 ядер, на 2–3 ядрах — общее с сетью и поддержкой |
| `cpu.layout.background` | `auto` | Ядра поддержки (фон Paper, spark, Amazake); сюда же переливаются потоки плагинов |
| `cpu.layout.support-nice` | `5` | Приоритет (nice, 0–19) фоновых потоков на ядре-подложке, где с ними работают потоки плагинов. `0` — приоритеты не трогать |
| `cpu.layout.resize-chunk-pool` | `true` | Подогнать размер пула чанков под число ядер `chunks` |
| `cpu.layout.ignore-processor-count` | `false` | Применять раскладку и без флага `-XX:ActiveProcessorCount` |

Вместо `auto` можно указать ядра вручную, номерами как в Linux (с нуля): `"0"`, `"1-3"`, `"1,2,5"`, `"0-3,8-11"`. Ядра, которые заняла ручная роль, убираются из автоматических ролей; свободные ядра достаются `background`. Ядра, недоступные серверу, и ошибки в списке Amazake пропускает и пишет об этом в консоль. После `/paper reload` размер пула чанков возвращается к настройке Paper: выполните `/amazake reload`, чтобы снова подогнать его (после `/reload` Bukkit это происходит само).

### Резерв и переезд тика

Раскладка закрепляет только потоки сервера. Другие процессы машины система по-прежнему может запустить на ядре `tick`: Discord-бот, база данных, бэкап, соседняя игра на том же хосте, прерывания сетевой карты, а на VPS — гипервизор, который отдаёт время ядра соседям (steal). Тогда главный поток стоит в очереди на своём же ядре, и тики растягиваются, хотя сам сервер ничего тяжелее не делает.

Поэтому часть ядер можно держать **в резерве**: Amazake не ставит туда ни одного потока, ядро остаётся пустым. Поток `Amazake Cores` каждые `check-seconds` секунд (по умолчанию 2) считает для ядра `tick`, сколько оно было занято всего (`/proc/stat`) и сколько из этого — сам главный поток (`/proc/self/task/<tid>/stat`). Разница — **чужая нагрузка**: другие процессы, прерывания и steal. Работа самого главного потока чужой не считается, как бы тяжело он ни тикал. Паузы сборщика мусора тоже не считаются: в паузе потоки `GC Thread#` могут работать на ядре `tick`, пока главный поток стоит, но это работа самого сервера, и время пауз (по данным JVM) из занятости ядра вычитается. Если чужая нагрузка больше `foreign-load-threshold` (по умолчанию четверть ядра) две проверки подряд, а резервное ядро почти свободно (занято меньше 10 %), главный поток **переезжает** туда. «Две проверки подряд» — это два соседних окна по `check-seconds`, в каждом из которых чужой нагрузки больше порога. Поэтому хватит и короткого всплеска, если он пришёлся на стык двух окон: при настройках по умолчанию — чуть больше секунды целого ядра (по полсекунды в каждом окне). Всплески короче секунды переезда не вызывают. Лишний переезд безвреден: главный поток просто остаётся на свободном ядре. Старое ядро `tick` становится резервом: Amazake убирает с него все потоки сервера (вместе с паузами GC), и ядро остаётся пустым до следующего переезда. После переезда следующий возможен не раньше чем через `cooldown-seconds` (30 с), чтобы тик не прыгал туда-сюда. Если резервные ядра тоже заняты, переезжать некуда: Amazake пишет об этом в консоль не чаще раза в 10 минут (со счётчиком повторов) и ждёт.

В консоли переезд — одна строка и пояснение на русском:

```
Amazake cores: tick moved cpu0 -> cpu11 (foreign load 48%, steal 3%)
```

В пояснении чужая нагрузка разложена по `/proc/stat`: другие процессы, прерывания (irq и softirq) и steal.

`/amazake cores` показывает резервные ядра и их загрузку, чужую нагрузку на ядре `tick` по последней проверке (сколько занял главный поток, паузы GC, другие процессы, прерывания, steal) и последний переезд. Если проверка не идёт, там написано почему: у `tick` не одно своё ядро, поток `Server thread` не найден или ещё не закреплён. В отчёте профайлера переезды отмечены на тепловой карте во вкладке «Ядра» (пунктир: контур — старое ядро, закрашенный кружок — новое), а резервные ядра подписаны «резерв».

Что это даёт и чего не даёт:

- **Помогает** против соседей по машине: бота, базы, бэкапа, второго сервера, прерываний на ядре `tick` и против steal на VPS, если гипервизор отнимает время именно у этого ядра. Главный поток уходит на ядро, где ему никто не мешает.
- **Не делает тяжёлый тик легче.** Если тик долгий из-за самой игры (фермы, мобы, редстоун, плагины), чужой нагрузки нет, и переезда не будет: ядро занято главным потоком, а это его собственная работа. Переезд на другое ядро её не уменьшит.
- Steal на VPS часто бывает на всех ядрах сразу: тогда резерв тоже занят, и переезд не поможет — нужен другой тариф или хост.
- Второй поток того же физического ядра (SMT) в `/proc/stat` ядра `tick` не виден: если мешает он, детектор этого не заметит.
- С SMT резерв никогда не берётся со второго потока физического ядра `tick`: сосед, занявший ядро `tick`, делил бы с переехавшим главным потоком одно физическое ядро. Поэтому на 6 ядрах с SMT (3 физических ядра) `auto` резерва не даёт: единственное ядро `background` — как раз второй поток ядра `tick`. Начиная с 8 ядер с SMT второй поток ядра `tick` свободен; тогда и второй поток резервного ядра остаётся свободным (в раскладке — «не заняты»), чтобы после переезда у главного потока снова было целое физическое ядро. Переезд выбирает только резерв, у которого свободен и второй поток.
- Резерв — это ядро, которое не работает на сервер. Поэтому `auto` держит резерв только от 6 доступных ядер (одно ядро), а на 3–5 ядрах — нет. На 3 ядрах лишнего ядра нет: резерв отнял бы единственное ядро у фона, плагинов и сети, и чанки, GC, сеть, плагины и фон делили бы одно ядро. Если на такой машине тику явно мешает сосед, резерв можно включить вручную: `cpu.reserve.count: 1` даёт `tick=[0]`, всё остальное на ядре 1, резерв — ядро 2.
- Ядра резерва берутся только у `background` (никогда у `tick`, `chunks`, своего ядра `plugins` и не у ролей, заданных вручную); если `background` пустеет, фон делит ядра с сетью, как на маленьких машинах (ядро `plugins` — только в крайнем случае). На 8 и 12 ядрах с SMT второй поток резервного ядра — ядро сети, поэтому оно тоже остаётся свободным, а сеть делит ядро с GC. Переезд работает, когда у `tick` ровно одно своё ядро.
- После `/amazake reload` раскладка считается заново. Если главный поток уже переехал, а ядро `tick` в новой раскладке то же и ядро, куда он переехал, по-прежнему в резерве, он остаётся там, где он сейчас (пауза `cooldown-seconds` после переезда тоже сохраняется). Если `cpu.layout.tick` поменяли или резерв выключили, главный поток идёт на ядро из новой раскладки.

| Настройка | По умолчанию | Что |
|---|---|---|
| `cpu.reserve.enabled` | `true` | Держать резерв и переносить на него главный поток. `false` — резерва нет, все ядра в раскладке |
| `cpu.reserve.count` | `auto` | Сколько ядер в резерве: `auto` — 1 от 6 доступных ядер, иначе 0; или число |
| `cpu.reserve.check-seconds` | `2` | Как часто проверять ядро `tick`, в секундах |
| `cpu.reserve.foreign-load-threshold` | `0.25` | Чужая нагрузка на ядре `tick` (в долях ядра), выше которой оно считается занятым |
| `cpu.reserve.cooldown-seconds` | `30` | Пауза после переезда, до которой следующего не будет |

## Как вносить изменения

1. `./gradlew applyAllPatches`. Появятся `paper-server/`, `paper-api/` и `amazake-server/src/minecraft/` — git-репозитории с кодом.
2. Правите код там и делаете коммиты внутри этих папок (один коммит — один патч).
3. Пересобираете патчи. Для API и одиночных файлов Paper — `./gradlew rebuildPaperPatches`. Полный список задач пересборки серверной части выводит `./gradlew tasks --all | grep -i rebuild`.
4. Коммитите изменённые файлы `*-patches/` в этот репозиторий.

Собственные классы Amazake (не патчи) лежат в `amazake-server/src/main/java/ink/hoka/amazake/`.

Отмечайте изменения в коде Minecraft и Paper комментариями `// Amazake - что и зачем`, а блоки — `// Amazake start - …` и `// Amazake end - …`. Так при обновлении Paper сразу видно, где наш код.

Проверить локально: `./gradlew runDevServer`.
